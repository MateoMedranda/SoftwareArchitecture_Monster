ESPECIFICACIÓN DE CASOS DE USO DETALLADO
A continuación, se muestra la Especificación de Casos de uso Detallado (ECUD) para el sistema de gestión bancaria “EurekaBank”, implementado mediante servicios RESTful en Java y persistencia en MySQL.

ECUD 01: AUTENTICAR USUARIO
A continuación, se muestra la especificación del caso de uso CU-01: Autenticar usuario.
Tabla 1. ECUD — CU-01: Autenticar usuario
ECUD — CU-01: AUTENTICAR USUARIO
Nombre caso de uso:
Autenticar usuario
Identificador:
CU-01
Descripción:
Permite al usuario registrado iniciar sesión mediante sus credenciales personales. El sistema valida las credenciales y devuelve un token JWT con la identidad y el rol del usuario.
Meta:
Verificar la identidad y establecer acceso autenticado a las funciones que corresponden al rol del usuario.

Gráfico:
Diagrama de casos de uso: CU_Sistema_General. Caso relacionado: Autenticar usuario.
Datos de entrada:
Nombre de usuario y contraseña.
Precondiciones:
El servicio REST de EurekaBank y la base de datos MySQL deben estar disponibles.
El usuario debe estar registrado y habilitado en el sistema.
Postcondiciones:
Éxito: el sistema devuelve una respuesta de autenticación exitosa con token JWT, identificador y rol del usuario.
Fallo: el sistema deniega el acceso y devuelve un error de autenticación; no crea una sesión válida.
Flujo básico — Inicio de sesión exitoso.
N°
Actor
Sistema
1
El usuario abre el cliente de EurekaBank que utilizará.
2
El sistema muestra el formulario de inicio de sesión.
3
El usuario ingresa nombre de usuario y contraseña y selecciona “Iniciar sesión”.
4
El sistema valida que ambos campos estén completos.
5
El sistema envía las credenciales en una solicitud REST POST /auth/login con contenido JSON.
6
El sistema verifica las credenciales contra los usuarios registrados y determina el rol del usuario.
7
El sistema genera un token JWT y devuelve la respuesta de autenticación.
8
El cliente almacena el token para incluirlo en el encabezado Authorization: Bearer en las solicitudes protegidas y muestra el menú correspondiente al rol.
Flujo alternativo
4a) El usuario deja vacío el nombre de usuario o la contraseña.
4a.1) El sistema indica que las credenciales son obligatorias y solicita completar los campos.
Vuelve al paso 3.
6a) El usuario no existe o la contraseña no coincide.
6a.1) El sistema deniega el acceso y devuelve un mensaje de autenticación fallida.
Termina.
6b) El servicio o la base de datos no están disponibles.
6b.1) El sistema informa que no fue posible completar la autenticación.
Termina.

5
El cliente elimina el token almacenado y muestra el formulario de inicio de sesión.

ECUD 03: GESTIONAR TRANSACCIONES
A continuación, se muestra la especificación del caso de uso CU-03: Gestionar transacciones.
Tabla 3. ECUD — CU-03: Gestionar transacciones
ECUD — CU-03: GESTIONAR TRANSACCIONES
Nombre caso de uso:
Gestionar transacciones
Identificador:
CU-03
Descripción:
Permite al usuario autorizado registrar ingresos, retiros y transferencias sobre cuentas bancarias. Las operaciones actualizan el saldo y dejan un registro auditable en la base de datos.
Meta:
Procesar movimientos monetarios de manera autorizada, consistente y atómica.
Estado:
Activo
Versión:
1.0
Autor(es):
Gabriel López, Mateo Medranda, Marcelo Pareja
Fecha creación:
05/11/2026
Fecha modificación:
05/11/2026
Gráfico:
Diagrama de casos de uso: CU_Sistema_General. Casos relacionados: Realizar Transacción, Verificar Cuenta y Verificar Saldo.
Datos de entrada:
Tipo de movimiento, número o identificador de cuenta y monto; para transferencias, cuenta de origen y cuenta de destino.
Precondiciones:
El usuario debe estar autenticado con token vigente.
El usuario debe tener rol ADMIN o CAJERO para registrar ingresos y retiros. Para transferir debe estar autenticado y tener permiso sobre la cuenta de origen.
Las cuentas involucradas deben existir y estar activas.
Postcondiciones:
Éxito: los saldos quedan actualizados y se registra la transacción o los movimientos de débito y crédito asociados.
Fallo: no se modifica parcialmente el saldo; se devuelve el error correspondiente.
Flujo básico — Registro de movimiento exitoso.
N°
Actor
Sistema
1
El usuario autorizado abre el módulo de transacciones.
2
El sistema muestra las opciones de ingreso, retiro y transferencia.
3
El usuario selecciona el tipo de operación e ingresa las cuentas y el monto solicitado.
4
El cliente envía la solicitud JSON al endpoint REST correspondiente, incluyendo el token JWT.
5
El sistema valida token, rol o permisos sobre la cuenta, formato de la solicitud, existencia y estado de las cuentas y que el monto sea mayor que cero.
6
El sistema obtiene el bloqueo exclusivo de disponibilidad de las cuentas y bloquea las filas necesarias durante la transacción JDBC.
7
El sistema valida el saldo cuando la operación lo requiere, registra el movimiento y actualiza los saldos en una transacción atómica.
8
El sistema confirma el resultado y devuelve los datos del movimiento o de la transferencia.
9
El cliente presenta el resultado y actualiza la información de la cuenta.
Flujo alternativo
5a) El token está ausente, expirado o revocado.
5a.1) El sistema rechaza la solicitud y devuelve un error de autenticación.
Termina.
5b) El usuario no tiene rol o permiso sobre la cuenta, la cuenta no existe o no está activa, el monto es inválido, el origen y destino son iguales o el saldo es insuficiente.
5b.1) El sistema rechaza la operación e informa el motivo sin modificar los saldos.
Termina.
7a) Ocurre un error al registrar el movimiento o actualizar los saldos.
7a.1) El sistema revierte la transacción JDBC y devuelve un error; los datos permanecen consistentes.
Termina.

CU-09: Consultar disponibilidad de cuenta.

Descripción:
Permite acreditar un monto positivo en una cuenta bancaria activa y registrar el movimiento como INGRESO.
Meta:
Incrementar el saldo de la cuenta y conservar el saldo anterior, el saldo posterior, el usuario que realizó la operación y la fecha.

Gráfico:
Diagrama de casos de uso: CU_Sistema_General. Caso relacionado: Realizar Transacción.
Datos de entrada:
Cuenta y monto mayor que cero. Solicitud REST POST /transacciones/movimientos con tipo INGRESO.
Precondiciones:
El usuario tiene sesión válida y rol ADMIN o CAJERO.
La cuenta existe, está activa y el usuario está autorizado para operar sobre ella.
Postcondiciones:
Éxito: el saldo se incrementa y se registra un movimiento INGRESO.
Fallo: el saldo y el historial no cambian.
Flujo básico — Ingreso exitoso.
N°
Actor
Sistema
1
El cajero selecciona “Registrar ingreso”.
2
El sistema solicita cuenta y monto.
3
El cajero ingresa los datos y confirma la operación.
4
El sistema valida token, rol, cuenta y monto.
5
El sistema bloquea temporalmente la cuenta para evitar operaciones concurrentes.
6
El sistema registra el movimiento INGRESO y actualiza el saldo de forma atómica.
7
El sistema devuelve la transacción creada y el saldo posterior.
Flujo alternativo
4a) El monto no es numérico, está vacío o es menor o igual que cero, la cuenta no existe, no está activa o el usuario no tiene permiso.
4a.1) El sistema rechaza el ingreso y devuelve el detalle del error.
Termina.
6a) Ocurre un error de base de datos.
6a.1) El sistema revierte la operación y no conserva cambios parciales.
Termina.

Descripción:
Permite transferir un monto positivo desde una cuenta de origen hacia otra cuenta de destino.
Meta:
Debitar y acreditar los saldos como una sola operación, dejando ambos movimientos vinculados por la referencia de transferencia.

Gráfico:
Diagrama de casos de uso: CU_Sistema_General. Caso relacionado: Realizar Transacción.
Datos de entrada:
Identificador o número público de cuenta de origen, identificador o número público de cuenta de destino y monto mayor que cero.
Precondiciones:
El usuario tiene sesión válida.
Ambas cuentas existen y están activas; el usuario tiene autorización sobre la cuenta de origen y saldo suficiente.
Las cuentas de origen y destino deben ser distintas.
Postcondiciones:
Éxito: el sistema actualiza ambos saldos y registra débito y crédito en una transacción atómica.
Fallo: se revierten los cambios y no queda aplicada parcialmente la transferencia.
Flujo básico — Transferencia exitosa.
N°
Actor
Sistema
1
El usuario selecciona “Realizar transferencia”.
2
El sistema solicita las cuentas de origen y destino, y el monto.
3
El usuario ingresa la información y confirma la operación.
4
El sistema valida token, permisos, cuentas, diferencia entre cuentas y monto.
5
El sistema obtiene bloqueos exclusivos en orden estable y bloquea las filas de ambas cuentas.
6
El sistema comprueba que el saldo de origen sea suficiente.
7
El sistema registra el débito y el crédito con una referencia común y actualiza los dos saldos dentro de una sola transacción JDBC.
8
El sistema confirma la transferencia y devuelve sus datos, incluidos los dos movimientos.
Flujo alternativo
4a) Una cuenta no existe, las cuentas son iguales, el monto no es válido o el usuario no tiene permiso sobre la cuenta de origen.
4a.1) El sistema rechaza la solicitud sin modificar saldos.
Termina.
6a) El saldo de origen es insuficiente.
6a.1) El sistema rechaza la transferencia e informa el motivo.
Termina.
7a) Se produce un error al guardar uno de los movimientos o actualizar los saldos.
7a.1) El sistema ejecuta rollback y no conserva ningún cambio parcial.
Termina.

ECUD — CU-03.4: REVERSAR TRANSACCIÓN
Nombre caso de uso:
Reversar transacción

CU-03.4
Descripción:
Permite registrar una transacción compensatoria para revertir un movimiento simple ya registrado. El movimiento original se conserva en el historial.
Meta:
Corregir una operación elegible mediante una nueva transacción auditable, sin borrar ni modificar el registro original.

Gráfico:
Diagrama de casos de uso: CU_Sistema_General. Caso relacionado: Realizar Transacción.
Datos de entrada:
Identificador de la transacción que se desea reversar y token JWT.
Precondiciones:
El usuario tiene sesión válida y permiso para reversar la transacción.
La transacción existe y es un movimiento simple elegible; no debe haberse reversado previamente.
Postcondiciones:
Éxito: se registra el movimiento inverso y se actualiza el saldo; se conserva el movimiento original.
Fallo: no se modifica el movimiento original ni el saldo.
Flujo básico — Reversa exitosa.
N°
Actor
Sistema
1
El usuario autorizado abre el historial y selecciona un movimiento simple.
2
El sistema muestra los datos del movimiento y la opción “Reversar”.
3
El usuario solicita la reversa.
4
El sistema valida token, permisos, existencia y elegibilidad del movimiento.
5
El sistema obtiene el bloqueo exclusivo de la cuenta y valida su estado y saldo aplicable.
6
El sistema registra la transacción compensatoria y actualiza el saldo de manera atómica.
7
El sistema confirma la reversa y presenta el nuevo movimiento asociado.
Flujo alternativo
4a) La transacción no existe, ya fue reversada o no es elegible para reversa.
4a.1) El sistema rechaza la solicitud y explica el motivo.
Termina.
5a) La reversa no es posible según el saldo o estado actual de la cuenta.
5a.1) El sistema rechaza la operación sin cambiar los datos.
Termina.

Filtro opcional cuentaId, usuarioId o identificador de transacción.

Actor
